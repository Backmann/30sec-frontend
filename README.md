# 30sec

Платформа для интеллектуальных игр с вопросами: живые турниры с человеческим
судейством, зрительский режим и одиночные игры между турнирами.
Продакшн: [30sec.org](https://30sec.org)

Проект состоит из двух репозиториев:

| Репозиторий | Роль |
|---|---|
| [`30sec`](https://github.com/Backmann/30sec) | API, игровой движок, БД, realtime, инфраструктура |
| [`30sec-frontend`](https://github.com/Backmann/30sec-frontend) | Веб-клиент |

---

## Что это

Турнир — это матч из вопросов, который ведут в реальном времени. Механика,
как она реализована в коде:

- **23 вопроса** в пуле турнира (`QUESTIONS_PER_TOURNAMENT`)
- матч идёт **до 12 очков**
- на каждый вопрос: **20 секунд** на чтение, затем **30 секунд** на ответ,
  затем блокировка приёма ответов
- ответы судит человек (админ/ведущий), а не автосравнение строк —
  принимаются формулировки, синонимы и частично верные ответы
- **синхронное раскрытие**: до момента раскрытия ни один игрок не видит
  чужих ответов, включая свой собственный статус
- зрители могут отвечать параллельно, их ответы учитываются отдельно
  (`SpectatorAnswer`) и не влияют на матч
- после матча — голосование за лучший вопрос, реакции, достижения, ранги

Интерфейс на трёх языках: **русский, английский, немецкий**.

## Сильные стороны

**Состояние живой игры переживает перезапуск.** Таймеры фаз живут в
`setTimeout` внутри процесса, но само состояние вопроса пишется в Redis
(`game:state:*`, TTL 6 ч). При старте модуль восстанавливает активные
турниры и заново заводит таймеры. Дедлайны хранятся как **абсолютное
время**, а не как «осталось N секунд», поэтому после перезапуска фаза
не начинается заново и не зависает.

**Статистика игрока производна от данных, а не накапливается.**
`PlayerStatsService` пересчитывает показатели из судейств
(`recalculate`, `recalculateMany`, `recalculateAll`). Счётчики нельзя
«разогнать» повторной отправкой события, и они не могут разойтись с
фактическими ответами — расхождение лечится пересчётом, а не ручной
правкой чисел.

**Ответы не утекают до раскрытия.** Подтверждение получения ответа
отправляется адресно, в сокеты конкретного пользователя
(`socketIdsForUser`), а не broadcast'ом в комнату турнира.

**Отзыв токенов работает.** В `User` есть `tokenVersion`, он попадает в
JWT как `tv` и сверяется при обновлении токена. Выход из аккаунта, сброс
пароля и удаление аккаунта инкрементируют версию — все ранее выданные
refresh-токены перестают действовать.

**Ограничение частоты запросов считается по реальному IP.**
`ProxyThrottlerGuard` берёт ключ из `X-Real-IP`, который проставляет
nginx. Без этого `req.ip` равнялся бы адресу контейнера nginx, и любой
лимит был бы общим для всего сайта, а не на пользователя.

**Пароли на argon2**, не bcrypt и не sha-варианты.

**GDPR по делу:** страницы privacy и terms, удаление аккаунта с реальной
очисткой (профиль, сессии с IP и координатами, уведомления),
анонимизация оставленных отзывов вместо их удаления.

**Разграничение доступа:** роли пользователей, журнал действий админа
(`AdminLog`), учёт сессий (`UserSession`).

## Тонкости, которые стоит знать

Это места, где поведение неочевидно. Почти каждая из них — след
реальной поломки.

**Rate limiter намеренно не читает `X-Forwarded-For` и `CF-Connecting-IP`.**
`X-Forwarded-For` nginx *дописывает*, поэтому клиент может подставить
своё значение в начало. `CF-Connecting-IP` подделывается, если
подключиться к origin напрямую, минуя Cloudflare. Доверенный источник
здесь только `X-Real-IP`, который nginx выставляет сам.

**Схема БД меняется исключительно raw SQL.** `prisma migrate reset`
на этом проекте уничтожит продакшн-данные. Изменения структуры
применяются вручную, `schema.prisma` приводится в соответствие отдельно.

**Файлы на диске — не файлы в контейнере.** После правки исходников
нужен `docker compose build`, иначе внутри образа выполнится старая
версия. Это особенно коварно для `prisma/seed.ts`: запуск сида без
пересборки прогонит прежний код и может перезаписать справочные
таблицы (ранги, достижения) устаревшими значениями.

**После пересоздания контейнера API нужен reload nginx.** Docker выдаёт
новому контейнеру другой внутренний адрес, а nginx держит прежний в
кеше резолвера и отдаёт `502 connect() failed (111: Connection refused)`.
Лечится `docker exec 30sec-nginx nginx -s reload`.

**API не пишет журнал HTTP-запросов.** Отсутствие записей в логах API
не доказывает, что запрос не дошёл — он мог прийти и получить ответ.
Факт запроса виден в логах nginx.

**Тестовые вопросы помечаются `theme: 'TEST'`.** Так наполняют турнир
для проверки механики, не смешивая тестовые вопросы с авторскими.
Их видно по теме и можно отфильтровать.

**Порты PostgreSQL и Redis привязаны к `127.0.0.1`** и недоступны
извне — снаружи открыты только 80 и 443.

**Дефолтных паролей в коде нет.** Репозиторий публичный, поэтому любой
литерал-заглушка был бы публично известным доступом. `docker-compose.yml`
требует `POSTGRES_PASSWORD` и `REDIS_PASSWORD` через `${VAR:?...}` —
без них стек не поднимется. Сид отказывается создавать администратора
без `ADMIN_PASSWORD` длиной не менее 12 символов. Это осознанный выбор:
упасть с внятной ошибкой лучше, чем молча запуститься с паролем,
который есть в открытом исходном коде.

**Секреты живут только в `.env` на сервере** (`chmod 600`), в git не
попадают, в history git их нет. `GOOGLE_CLIENT_ID` во фронтенде
захардкожен намеренно — в OAuth это публичный идентификатор, а не секрет.

## Статус

Проект работает, но открыт не для всех: он снят с индексации поисковыми
системами, пока доводится логика и защита. Основное направление
развития — интеллектуальные игры в перерывах между турнирами и уличные
квесты.

Из ближайших планов: автотесты (сейчас их нет) и оптимизация выдачи
на части эндпоинтов. Мажорные обновления NestJS, Next.js и Sentry
отложены осознанно — они требуют `--force` и ломают сборку, а
заявленные в них уязвимости в этой конфигурации не применимы.

## Этот репозиторий: веб-клиент

Next.js 14 на App Router. Docker-окружение и nginx лежат в репозитории
[`30sec`](https://github.com/Backmann/30sec) — этот контейнер
поднимается оттуда же.

### Страницы

```
/                     лендинг
/auth/login  /auth/register  /auth/verify-email  /auth/forgot-password
/dashboard            личный кабинет
/profile              профиль, настройки, удаление аккаунта
/game/[id]            участие в матче
/live/[id]            живая трансляция турнира
/watch/[id]           зрительский режим с возможностью отвечать
/vote/[id]            голосование за лучший вопрос
/leaderboard          таблица лидеров
/player/[nickname]    публичный профиль игрока
/admin                админ-панель
/admin/live/[id]      пульт ведущего: судейство и управление фазами
/contact  /privacy  /terms
```

22 компонента в `src/components/`, состояние на Zustand,
API-клиент и работа с токенами — в `src/lib/api.ts`.

### Realtime-события

Клиент слушает: `question_started`, `phase_changed`, `timer_tick`,
`answer_submitted`, `answer_status`, `question_locked`,
`judgement_made`, `judgements_revealed`, `score_updated`,
`match_finished`, `tournament_started`, `tournament_finished`,
`reactions_updated`, `game_state_restore`.

`game_state_restore` — как раз тот механизм, что возвращает клиента
в правильную фазу с правильным остатком времени после переподключения
или перезапуска сервера.

### Тонкости клиента

**Обновление токена дедуплицировано.** `refreshPromise` в `src/lib/api.ts`
гарантирует, что несколько параллельных запросов с истёкшим access-токеном
инициируют одно обновление, а не гонку из нескольких.

**Выход из аккаунта чистит токены синхронно** — до `await` серверного
вызова, потому что вызывающий код `logout()` не дожидается промиса.

**Язык `<html lang>` правится на клиенте** компонентом `HtmlLangSync`:
на сервере известен только язык по умолчанию.

### Запуск локально

```bash
npm install
cp .env.example .env.local   # заполнить NEXT_PUBLIC_API_URL и NEXT_PUBLIC_WS_URL
npm run dev
```

Обе переменные попадают в клиентскую сборку и по устройству Next.js
публичны — секретов среди них нет и быть не должно.

Нужен запущенный API — см. репозиторий
[`30sec`](https://github.com/Backmann/30sec).
